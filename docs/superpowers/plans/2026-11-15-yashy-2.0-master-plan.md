# Yashy 2.0 Master Plan (Index)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Yashy a language you can build and ship a real product in — fast enough to stay in flow, complete enough that the standard library is a product, powerful enough for systems and services, and legible enough that a person and an agent can both change the same code safely.

**Architecture:** Fourteen phases in fifteen slices, ~119 weeks. **Flow** first (test harness, daemon, incremental build, LSP error recovery), then **language power** (generic traits, associated types, default methods, pattern completeness, typed pointers and a written aliasing model), then the **product stack** (collections, text/JSON, TLS/HTTP, SQL, application libraries), then **quality, concurrency**, **representation (11A)**, **code generation (11B)**, **reach**, **AI-native v2**, and finally **self-hosting, the language reference, and the 2.0 release**. The 1.0 identity is unchanged: no garbage collector, no borrow checker, no exceptions, no inheritance, no operator overloading, no procedural macros, no `dyn`, no async traits, no pluggable runtime. Speed is a standing budget from Phase 1 and a hard target in Phase 11B; determinism is a written contract from Phase 4 onward.

**Tech Stack:** Rust workspace (one crate per compiler stage), LLVM via `clang`/`llc`, the C runtime shim, Yashy-source stdlib and packages, a content-addressed cache, a memoised query pipeline, and a local/static package registry. No new compiler runtime dependency without a plan.

**Spec:** [`../specs/2026-11-15-yashy-2.0-design.md`](../specs/2026-11-15-yashy-2.0-design.md) — read it before any phase. The 1.0 design remains the authority on identity: [`../specs/2026-10-27-yashy-master-design.md`](../specs/2026-10-27-yashy-master-design.md).

## Global Constraints

Every task's requirements implicitly include this section.

- **The 1.0 identity is unchanged.** No garbage collector, borrow checker, exceptions, implicit coercion, operator overloading, class inheritance, procedural macros, `dyn`/vtables, async traits, or pluggable runtime.
- **Ownership is explicit.** `move` transfers; `defer` releases at scope exit; arrays, maps, channels, mutexes and built strings use `.free()`.
- **Errors are values.** `Option[T]` and `Result[T, E]`; `?` propagates. No exceptions. A builtin never answers with a sentinel.
- **Safe code has no uninitialised read.** `alloc` zeroes from Phase 4 on; uninitialised memory is `unsafe alloc_uninit` and is inventoried.
- **Aliasing is conservative by default.** Owning pointers are unique by linearity; `noalias` is `unsafe`/`extern`-only; safe code cannot declare an alias promise it can break. Every emitted attribute is named by `--opt-report`.
- **Determinism is a contract.** Same program, inputs, declared capabilities and target ⇒ same bytes, exit code and event trace. Maps iterate in insertion order, hash seeds are fixed, clock/env/entropy are capabilities, and `--deterministic` fixes the scheduler. A change that breaks it is a breaking change.
- **Speed is a budget, not a phase.** Every phase carries a benchmark row and a compile-time row; no pass lands without a row; no feature lands with an unexplained regression. Inlining is a measured pass, never a source-level `inline` keyword.
- **One fact, two renderings, and one catalog.** Every new verb and diagnostic has a human form rendered from its JSON model; every diagnostic code has a page, a catalog entry, an `explain --json` record and a triggering test; schema changes are additive only.
- **Rules are traceable.** Every rule has an ID; every code, conformance case and stdlib function names the rule it covers; `yashyc trace --json` generates the matrix and CI fails on an orphan.
- **Surface syntax is BPE-audited.** Every keyword, operator and delimiter is one token in the tokenizers agents use; new forms are measured before they ship.
- **Tests are ordinary programs.** A file under `tests/` is a Yashy program with `main`; exit 0 is a pass. No `#[test]` attributes or test macros in `.ya` files.
- **One rule, one implementation.** `yashy-verify` remains the only judge of ownership; a rule duplicated across crates is a defect.
- **No new compiler runtime dependency without a plan and a reason.** A C library a package wraps is a package dependency: pinned, audited, and recorded in the lockfile and SBOM.
- **A malformed program produces a diagnostic, never a Rust panic.** The `never_panics` suite enforces this.
- **Every feature ships with tests, docs, diagnostics, and a machine-readable form.**
- **Both operating systems or it is not done:** every gate runs on Windows and Linux. macOS gates run where the phase says so; macOS is claimed only when a signed and notarised archive ships.
- **No unproven claim.** No safety claim without a proof or a test; no speed claim without a number from both operating systems.
- **No silent scope growth.** A new idea goes into the next phase plan, not the current one.
- **Format touched files.** `cargo fmt --all --check` has pre-existing drift; do not reformat unrelated files.

## Review Focus

The eight failure modes most likely to bite a user of 2.0, most likely first.
Each has a test in the task that owns the code.

1. **A fast test runner that hides a failing test.** One harness is not one
   process. A crash, a non-zero exit, a timeout, a leaked allocation, or a test
   that writes to stdout must be attributed to the test that caused it. The 1.0
   test corpus is the differential: same tests, same results, 600× faster.
2. **An incremental cache serves a stale binary.** The key covers source bytes,
   flags, compiler version, target, runtime, package versions, features and
   environment. `yashyc cache verify` recomputes it; CI never trusts a cache it
   did not create. A stale hit is a wrong binary, which is a P0.
3. **A structured edit corrupts source.** Every edit carries byte spans and the
   expected hash of the text it replaces. Apply validates before and after, and
   refuses on a mismatch. There is no shell, no path outside the workspace, and
   no edit that is not expressed as a patch.
4. **A new library returns a sentinel on failure.** `read_file` returning `""`
   on a missing file, `getenv` returning `""` for unset, `parse_i64` returning
   `0` for garbage — all are the 1.0 mistake. Every fallible function answers
   `Result` or `Option`, and the stdlib gate rejects a doc comment that names
   `""`/`0` as its failure value.
5. **A performance pass buys one row by selling another.** Every registered
   pass is held to its own benchmark row, measured interleaved on both OSes;
   compile-time rows are normalized against a same-run reference. No pass
   without a row; no row without a number.
6. **An optimizer assumption miscompiles safe code.** The largest new source
   of wrong binaries in 2.0 is an aliasing or layout promise the language never
   made. Owning pointers are unique by linearity, `noalias` is `unsafe`/`extern`
   only, `repr(C)` is never reordered, and the alias corpus fails on any
   attribute that `--opt-report` cannot justify.
7. **The determinism contract quietly stops being true.** A hash seed, a map
   order, an address in a message, a scheduler that changes with thread count —
   each is a one-line change that makes every agent run and every diff unstable.
   The corpus runs twice and compares bytes and traces; `--deterministic` at 1
   and 4 workers must agree.
8. **Surface syntax drifts away from the tokenizers agents use.** A keyword that
   splits into three BPE tokens taxes every prompt and every generated line.
   Every keyword/operator is one token in three tokenizers, the corpus is
   measured, and a spelling is rejected only with its number recorded.

**Detail falls off with distance, deliberately.** Phases 1–3 are executable to
the task: they name files, interfaces, tests and commands. Phases 4–8 name
deliverables, gates and the interfaces that matter. Phases 9–14 name outcomes
and gates, because their shape depends on everything before them. A phase plan
is **revised at phase start**, never rewritten from scratch: the revision
re-reads the code as it exists that day, keeps the outcome and the gate, and
updates task detail. The spec and this index are what a revision may not
contradict.

**A phase is not started until its predecessor's gate has passed and its plan
has been revised.** The exception is a written exception record (see Gate
protocol).

Total ≈ 119 weeks.

**Why this order.** Flow first because every later phase is developed and
demonstrated on this loop; 1.0's test runner misses its budget by more than
600×. Language power before the product stack because the stdlib is the first
consumer of generic traits, associated types and default methods; building
collections and serialization on non-generic traits would force the second
stdlib rewrite that 1.0's ordering avoided. Product before concurrency and
performance because a language with no TLS, SQL, JSON or test framework is not
a product, and optimising a language nobody can build in measures the wrong
thing. Concurrency before performance because checked-arithmetic vectorisation
must coexist with the parallel runtime and the race proofs. Representation
(11A) before code generation (11B) because a pass may only spend a memory fact
the language actually made — layout, uniqueness, provenance, stack lifetime —
and building the optimizer first would teach it to assume a model that is not
there. Speed is a standing budget from Phase 1, not a single phase. Reach before
AI-native because the semantic graph must include the new language forms and
the new libraries. Self-hosting and the spec last because both are checks on a
language that has stopped moving, and because they are the two most cuttable
phases.

## Gate protocol

A phase is complete when all six hold on a clean checkout:

1. The phase's gate commands pass on **Windows and Linux**; macOS where the
   phase says so.
2. The phase's demo runs: a copyable command with expected output in the phase
   plan.
3. `cargo test --workspace` is green on both operating systems.
4. No P0 is open; `never_panics`, `sandbox_escape`, `repro-check`, the alias
   corpus and the determinism differential are green.
5. The commit hash is recorded in this table and in the phase plan.
6. The progress ledger at `.superpowers/sdd/<date>-<slice>/progress.md` is
   current.

A missed gate is recorded as an **exception**: a dated entry in the phase plan
naming the gate, the reason, the owner, and when it will be re-run. Silent
slips are not permitted; a phase with an open exception cannot be marked
complete.

Every phase also carries one experience slice, one benchmark or measurement
row, one documentation page, one machine-readable form for every new verb or
diagnostic, and one traceability link from each new rule to its code and test.
`docs/architecture.md` is updated in the same phase as any sentence it makes
false.

## Cut order

When a phase runs long, cut in this order:

playground upgrade → GUI/ML/media packages → Android/iOS/bare-metal targets →
Python/Node interop → C++ interop → full self-hosting (keep the front-end
differential) → WASM/WASI (keep the browser proof) → generators/`yield` →
const generics beyond fixed arrays → default methods/supertraits (keep generic
traits and associated types) → HTTP/2 and WebSocket → MySQL/Redis → email/jobs/
auth → coverage/bench/fuzz → REPL → workspaces/features → extra editor plugins →
`yashyc task` → sampling profiler (keep the counter profiler) → `doc --serve` →
BPE corpus percentage (keep the keyword/operator rule).

**Never cut:**

- The instant feedback loop: test harness v2, incremental build, watch/daemon.
- LSP, debugger and profiler as a set.
- Package signing, SBOM, audit and reproducible builds.
- The core stdlib: collections, JSON, HTTP/TLS, SQL, CLI, test, log, crypto.
- Generic traits and associated types.
- Concurrency proofs and the TSan differential.
- Checked-arithmetic vectorisation and the per-pass benchmark gate.
- The memory model: typed pointers, the written aliasing rules, layout reporting,
  zeroed allocation, stack/heap reports.
- The determinism contract and its differential.
- The traceability matrix, the error catalog and machine-readable diagnostics.
- MCP v1, structured edits, semantic graph, context packs, sandbox v1.
- Both-OS CI, the benchmark gate, and the no-false-positive gate.
- The 2.0 spec, conformance suite and migration path.
- The identity rules in the design's §4.

## First 30 days

The first slice is Phase 1. Start with these five tasks, in order, because each
one makes the next cheaper:

1. **Measure and close T3.** Build the one-harness test runner, preserve
   per-test isolation, and record the 101-test fixture on Windows and Linux.
   Acceptance: 100 tests < 2 s; the 1.0 tests produce the same results.
2. **Add the daemon and `watch`.** `yashyc serve` keeps the source map, query
   database and cache warm; `yashyc watch` re-checks on change and prints
   diagnostics. Acceptance: edit-to-diagnostic < 50 ms on a 10k-line project.
3. **Make incremental build real.** Cache per-module object files and link only
   what changed; keep the one-shot path. Acceptance: second build < 100 ms;
   byte-identical output with and without the daemon.
4. **Normalize compile-time rows.** Add a same-run reference (clang on the same
   program) and an interleaved A/B measurement; gate at 20% honestly.
   Acceptance: `benchmarks/ci.*` fails on a 30% regression and passes on noise.
5. **Give the parser error recovery.** The LSP must answer while the code is
   incomplete. Acceptance: `cargo test -p yashy-lsp` has a recovery corpus; a
   half-typed `fn` still hovers, completes and re-checks.

## Starting a phase

1. Read the spec §6 row for the phase and the previous phase's "Outcome".
2. Read the current code the phase touches; the revision is written from
   today's code, not from the spec's memory of it.
3. Revise `docs/superpowers/plans/2026-11-15-phase-<id>-<name>.md` in place,
   keeping its header, outcome and gate.
4. Run its self-review against the spec: every spec requirement in that phase
   maps to a task.
5. Set this table's Status to `in progress`, then execute with
   `superpowers:executing-plans` or `superpowers:subagent-driven-development`.
