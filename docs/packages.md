# Packages

A Yashy program is a file. A project is a directory with a `yashy.toml`, and
a package is a project another project depends on. There is no virtual
environment, no build script and no version solver: a dependency names an
exact version, a path or a commit, and resolution either finds that exact
thing or stops with a diagnostic.

The compiler has to keep building offline, so the manifest reader is a
documented subset of TOML written by hand. The lockfile, the store and the
local registry are files on disk; none of them needs a service.

## The manifest

```toml
[package]
name = "hello"
version = "0.1.0"
description = "One greeting, on stdout"

[dependencies]
http = "0.3.1"
text = "0.1.0"

[dependencies.net]
path = "../net"

[dependencies.extra]
git = "https://example.invalid/extra"
rev = "0123456789abcdef0123456789abcdef01234567"
```

The grammar, in one block:

```text
file       := line*
line       := ws (comment | table | array-table | assignment) ws comment? ws
table      := '[' key ('.' key)* ']'
array-table:= '[[' key ('.' key)* ']]'
assignment := key ('.' key)* '=' ws value
key        := bare-key | '"' basic-string '"' | "'" literal-string "'"
value      := string | integer | boolean | array
array      := '[' ws (value ws (',' value ws)* ','?)? ']'
comment    := '#' any
```

Bare keys are letters, digits, `_` and `-`. Strings are single-line: a basic
string understands `\n`, `\r`, `\t`, `\\` and `\"`, and a literal string
understands nothing. There are no inline tables, no multi-line strings, no
floats and no dates. `[[name]]` appends one table to an array and is the form
the lockfile uses; a plain `[table]` may not repeat. The whole file is capped
at 1 MiB, and every rejection is [E1800](errors/E1800.md) with a line and a
column.

Versions are exact pins: `1.2.3`, never `^1.2.3`, `~1.2.3`, `*` or a range.
A git dependency names a commit, not a branch. Unknown tables and keys are
refused, so a misspelled `[dependecies]` cannot silently vanish.

A package's modules are found under `src/` when it has one, and under its root
otherwise. During a build the entry directory and every resolved package root
are put at the front of `YASHY_PATH`, so `import net;` finds the `net` package
without any manual environment setup.

## The lockfile

`yashy update` resolves the manifest and writes `yashy.lock`:

```toml
# This file is generated by `yashy lock`; do not edit it by hand.
version = 1

[[package]]
name = "http"
version = "0.3.1"
source = "registry+file:///home/you/demo-registry"
hash = "sha256:..."
dependencies = []

[[package]]
name = "net"
version = "0.2.0"
source = "path+../net"
hash = "sha256:..."
dependencies = ["http 0.3.1"]
```

Only dependencies appear: the root project is the manifest, not a locked
package. Packages are sorted by name then version, every dependency list is
sorted, endings are LF, and the `sha256:` hash is over a canonical source
tree: sorted paths, CRLF normalised, no mtimes and no permissions. Two
checkouts of the same package therefore produce the same lock bytes on both
operating systems.

`yashy lock --check` compares the manifest with the lock and exits 1 with
[E1802](errors/E1802.md) when a version, source or hash differs. `yashy build`
and `yashy run` resolve through the same lock when one is present, so a build
never quietly uses a different tree from the one the lock records.

## Resolution and the store

```text
yashy update [--offline] [dir]   resolve the manifests and rewrite yashy.lock
yashy fetch  [--offline] [dir]   put every package in the store, without building
yashy add <name> --path <dir>    append a path dependency, then update
yashy add <name> --git <url> --rev <commit>
                                 append a pinned git dependency, then update
yashy add <name>@<version> --registry <dir>
                                 append a registry dependency, then update
```

A path dependency is read in place. A git dependency is cloned into a store
keyed by `(url, rev)`, checked out at that commit and made read-only. A
registry dependency is looked up by exact version, its tarball hash is checked
and the tree is unpacked into the store. A dependency cycle is
[E1801](errors/E1801.md) and prints the path it followed.

`--offline` never invokes git or touches the network: a package that is not
already in the store stops the build with [E1803](errors/E1803.md), which
names the package, its pin and the command that would fetch it.

The store lives under `YASHY_PACKAGE_STORE` when set, and otherwise under the
compiler's cache directory: `YASHY_CACHE_DIR/packages`, or the platform
convention (`%LOCALAPPDATA%/yashy/packages`,
`$XDG_CACHE_HOME/yashy/packages`, `~/.cache/yashy/packages`).

## Audit

```text
yashy audit [dir] [--json]
```

The audit reads the resolved graph, not the manifest alone, and checks four
things: every dependency has an exact version, every source is a path, git or
registry source the manifest may spell, the lock matches the manifest, and no
dependency comes from an untrusted registry. A finding is
[E1804](errors/E1804.md); a clean project prints one line:

```text
$ yashy audit
ok: 3 packages, 18422 bytes
```

`--json` prints the stable model: `schema_version`, `ok`, `packages`,
`source_bytes`, and `findings` (each with `code`, `package`, `detail`). The
audit exits 0 when `ok` is true and 1 otherwise, so it fits a CI step without
parsing output.

## A local registry

A registry is a directory. `index.json` lists `name`, `version`, `hash` and
`description`; `packages/<hash>.tar` holds the tree. Publishing writes the
tarball and the index through staging files and renames them into place, so a
reader never sees half a package. A duplicate name and version with a
different hash is an error; the same pair with the same hash is an idempotent
republish.

```text
$ mkdir -p demo-registry
$ yashy publish packages/cli --registry "$PWD/demo-registry"
published cli@0.1.0 sha256:6a1e... to /home/you/demo-registry
```

Publishing takes its name, version and description from the package's own
`yashy.toml`, and hashes the whole tree. A second consumer then names it by
exact version:

```text
$ yashy init consumer
$ cd consumer
$ yashy add cli@0.1.0 --registry "$PWD/../demo-registry"
$ yashy build main.ya
```

`add` writes the dependency into `yashy.toml`, sets `YASHY_REGISTRY` for the
update it runs, fetches the package into the store and rewrites `yashy.lock`.
From then on the build reads the store, so an ordinary `yashy build` does not
need the registry. A later `yashy update` does: set `YASHY_REGISTRY` to the
registry directory, or leave it unset to use `store/registry`.

```text
$ yashy build --offline main.ya
$ yashy audit
ok: 2 packages, 8301 bytes
```

`--offline` is the proof that the store is warm: if anything is missing, the
build stops with [E1803](errors/E1803.md) naming it rather than reaching for
the network.

## A hosted registry

The registry a release publishes is a *static* index: `index.json` and one
tarball per package. There is no service, no database and no upload API --
the directory is the registry, and the URL of the directory is the registry's
address.

Reading from a URL works the same way as reading from a directory:

```text
$ cd consumer
$ YASHY_REGISTRY=https://packages.example.com/ yashy add cli@0.1.0
$ YASHY_REGISTRY=https://packages.example.com/ yashy build main.ya
```

The package's tree hash is the integrity check: the tarball is unpacked into
the store, the tree is hashed, and the hash must be the one the index names. A
tarball that was changed on the way is refused, and the build stops with the
two hashes in the message.

An `https://` registry is fetched over TLS, and the fetch fails rather than
falling back to plaintext. The compiler ships no TLS stack of its own, so the
fetch uses `curl`; a machine without it gets a message that names it.

Publishing stays local. A package reaches a hosted registry by a pull request
to the registry's repository, reviewed by a person:

```text
$ scripts/publish-registry.sh registry
publishing bench
publishing cli
publishing fuzz
publishing http
publishing net
publishing test
published 6 package(s) into registry
```

## What the prototype does not do

- There is no version solver. Every dependency is an exact pin.
- `--registry` takes an absolute path, a `file://` URL, or an `http(s)://` URL
  to read from. Publishing needs a directory it can write to.
- A registry entry carries no signature beyond its content hash, so trust is
  the decision to point `YASHY_REGISTRY` at that registry.
- `yashy publish` writes the tree as it is; it does not run the package's
  tests first. Run `yashy test` before publishing.
